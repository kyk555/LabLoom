# 增量开发与交付

## 一、动手前三步

### 1. 读现场（不许凭印象改）

| 要读的 | 为什么 |
|---|---|
| `README.md` | 项目定位、当前阶段、合规红线、下一步 |
| `docs/01-验证计划.md` | 这轮要验证什么、决策门是什么（别做计划外的事） |
| `docs/02-技术构想.md` | 分层边界（IR / 校验 / 渲染），别把校验逻辑写进渲染里 |
| `.clinerules/01` | 内容准确性红线，动手前先知道自己不能碰什么 |
| 要改的代码与它所在目录的 `README.md` | 现有约定、踩过的坑 |

### 2. 先复述需求，等确认再动手

用中文复述「要做什么、为什么、动哪些文件、验收标准是什么、缺什么信息」。
需求要素自查：**目标 / 涉及模块 / 样本或数据 / 输出形态 / 验收标准 / 是否触碰合规红线**。

### 3. 说清影响面

- 是否改到共享规则（校验规则、IR 字段、安全模板）→ 会则跑全量回归。
- 是否动已登记的样本、验证记录、已发布产物 → 会则**先问**。

## 二、三条原则

| 原则 | 本项目怎么落 |
|---|---|
| **可核验** | 每个学科结论都要有依据（教材 / 课标 / 权威资料），能被人当场查证 |
| **可复现** | 同一份 IR + 同一套规则 → 同一份输出；样本带版本与指纹 |
| **可归因** | 出错时说清是哪一层（生成 / 校验 / 渲染 / 依据缺失），不许只报「生成的不准」 |

## 三、禁止臆造（第一红线）

- 学科事实（方程式、参数、生理过程、课标条款）**先查再写**；查不到就写「待核实」。
- API / 文件路径 / 字段名 / 版本号一律先看源码与实际文件；搜得到 + 跑得通才算数。
- 本项目没有的能力（自动评分、替代教师判断、实时演示）直接说「没有」，不要编。

## 四、分层：不许穿透

| 层 | 位置（计划中） | 规矩 |
|---|---|---|
| 内容 | `样例/` / IR 文件 | 只存结构化事实，不掺渲染代码 |
| 校验 | `校验/` | 纯函数：IR 进、错误清单出；**不发网络请求、不写文件、不取当前时间**（日期当参数传入） |
| 渲染 | `渲染/` | 只读 IR，不内联自己的「常识」；IR 缺字段就报错 |
| 文档 / 工具 | `docs/`、`工具/` | 不参与产品运行时 |

- 可调参数（阈值、学段映射、安全规则开关）集中在配置区，不许散在函数体里。

## 五、范围纪律

- 改动范围 = 需求范围；范围外的问题**只报告不修改**，禁止顺手重构、改测试期望值、删无关文件。
- 一次改多个文件时，**逐文件给出改动摘要**（哪个文件、哪个函数、行为差异），不允许「改了 N 个文件只说 1 个」。
- 交付前对照第一步的复述清单逐条核对，防止多轮之后忘记开工时的约束。

## 六、失效模式自查（针对 AI 辅助）

- 🔴 **幻觉接口 / 幻觉事实**：编出不存在的函数、课标条款、参数
- 🔴 **静默降级**：抓不到就跳过、缺字段就给默认值
- 🔴 **自证式测试**：测试断言实现本身，改坏了也不红
- 🔴 **越权改动**：顺手改样本、改别人的记录
- 🔴 **无出处数字**：报告里出现查不到来源的数值
- 🔴 **口径漂移**：同一指标在两份文档里定义不同

## 七、明确不适用（防照搬参考项目）

本项目**没有**：回测、因子、实盘下单、前视偏差、净值 / 夏普 / 回撤这类指标。
从 `allweather` 借来的只有**工程纪律**（留痕、可核验、范围纪律、离线测试、交付五段式），不借它的业务口径。

## 八、提交信息怎么写

```
<类型>: <一句话>
- 改了什么（文件级）
- 为什么（对应 issue 编号 / 验证轮次）
- 影响：哪份样本 / 哪条规则 / 哪个结论
- 验证：跑了什么、结果如何
```

类型：`docs`（文档）/ `feat`（功能）/ `fix`（修错）/ `test`（测试）/ `chore`（杂务）。
